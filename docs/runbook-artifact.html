Testing it

Five levels, ascending in cost. The numbering is the sequence: each one assumes the ones above it passed.

  1. Click it

    30 seconds

    Open the URL, go to live, then run a brief and send one. Credential mints, card fetches and invocations animate as they happen. Then review to read the lineage and open the cited sources.

  2. The suite

    8 seconds, no cloud
    python3 -m pytest -q   # 349 passed, 15 skipped
ruff check .           # 2 findings, both pre-existing

    Entirely hermetic. Includes the guards that matter: SSRF refusals on the source fetcher, the researcher/coordinator role boundary, and node --check over the page's inline JavaScript.

  3. The local mesh

    real A2A, no spend
    ./infra/run_mesh.sh start                 # :10001 :10002 :10003
python3 -m coordinator.cli "your topic"
./infra/run_mesh.sh stop

    direct-brain, so drafts are canned and identical on all three. Exercises the protocol and the orchestration, not the models. To watch it in the UI, run a local master with python3 -m uvicorn coordinator.service:app --port 8099.

  4. The demo

    the part worth watching
    ./infra/demo.sh

    Four acts, and acts 3 and 4 are the argument: a cloud goes offline and the run degrades instead of failing, and a cloud phones it in and the judge declines to pick it. Any demo shows three green ticks.

  5. The controls

    ~10 min, spends money
    ./infra/deploy_gcp.sh verify

    Each leg alone with its credentials, then each with its credential removed. Reads the container's exit code: 0 answered, 3 denied, anything else prints THE CONTROL DID NOT RUN.

    Trust this least on faith and most in practice. On 2026-08-13 it caught the Azure agent serving the internet while every other signal was green — and it had itself been reporting false passes for two unrelated reasons before that.

Testing the judge, not the mesh

Whether the mesh runs is the easy question. Whether the judge is any good is the open one.

curl -s $URL/api/calibration | python3 -m json.tool

# or re-rank the whole stored corpus with a second judge, mutating nothing
python3 -m evaluations.rejudge --judge llm

Rank a few runs by hand in the review tab and agreement_rate becomes a real number. If the human and the judge diverge, the rubric is wrong — which is a finding, and currently the biggest untested claim here. One review is not a calibration, and the field says reviewed: 1 so you can decline to read it as one.

rejudge is the cheaper half of the same question, and it has already been run: it answers "is this finding an artifact of one scorer?" without touching the record. It cannot answer "is either scorer right", which is what the review tab is for.

Deploying

PUBLIC=1 MODEL_MODE=llm OTEL_TRACES_EXPORTER=gcp ./infra/deploy_gcp.sh deploy
./infra/deploy_gcp.sh wire            # fold AWS and Azure in

MODEL_MODE=llm ./infra/deploy_aws.sh deploy
MODEL_MODE=llm ./infra/deploy_azure.sh deploy
./infra/deploy_azure.sh foundry       # the model deployment
./infra/deploy_azure.sh fic           # Entra federated credential
./infra/deploy_azure.sh auth          # ENFORCE Entra on the ingress

deploy_azure.sh auth is not optional and is easy to skip. fic decides who can obtain a token; auth decides whether the app demands one. Ship only the first and the leg reports entra-fic while answering anyone who asks. That is exactly what happened on 2026-08-13.

Changing the judge, the rubric, the pass mark, the instruction or the search provider changes what every subsequent run means. The report warns on mixed judges, mixed rubric versions and mixed prompt versions; it cannot warn about the rest.

What is true, and what is not

The difference is not obvious from the UI, which renders a measured result and an unvalidated one identically.

  • MeasuredThree native agents, three federation modes, each with a positive and a negative control behind it — measured 2026-08-13, and not re-run since the agents were rebuilt for prompt v2 and v3.
  • MeasuredThe wrong-audience probe — a valid token minted for the wrong aud — was run on the GCP leg only. AWS and Azure have the credential-removed control and not this one.
  • MeasuredThe judge loop gates a draft and sends it back, and the mesh acts on the critique.
  • Retracted"The loop lifted Gemini 13.8 → 21.1" is withdrawn as evidence the loop improves drafts. Of the three rewrites that can be inspected, two began from a 31-word Vertex 429 error scored as a draft and "improved" by being retried. The loop is shown to recover a failed leg; improving a merely weak draft rests on one case.
  • MeasuredTraces are live: wire events reach the view before their leg finishes.
  • MeasuredInstruction v2/v3 moved AWS from 0 searches in 7 of 7 drafts to 3 zero-search drafts in 16 — never to usually, not never to always. Six sampled citations resolved.
  • OpenThe six-search budget is binding on Gemini. It spends all six in every v3 run, so the ceiling is now shaping one participant's drafts and the comparison is partly a comparison of who reaches it.
  • ContestedThe best-of-breed claim did not survive a second scorer. Re-ranking the same 24 runs with the model judge: Azure wins 87% and AWS 0%, against 43%/33% under the rubric, and AWS’s regret goes from 1.32 to 9.38. Under a model judge a panel is not justified on quality. Availability is unaffected — no judge changes whether a draft existed.
  • OpenThe rotation is not statistically distinguishable from random. 10/8/6 wins over 24 runs gives χ²=1.00 on 2 df — and that test is generous, since GCP answered only 14 of the 24 and cannot win one it did not answer. The defensible claim is that the winner is unpredictable, not that it rotates systematically, and unpredictability is the stronger argument for a panel anyway.
  • OpenAll 24 runs are one topic domain — batteries, hydrogen, solar, reactors. Nothing here has been tried on a different kind of question.
  • OpenThe rubric is uncalibrated. Its weightings were chosen by argument. agreement_rate is the check and it stands at one review.
  • OpenThe model judge has judged the stored corpus, never a live run. rejudge loads the same LlmJudge the service would, offline, over recorded drafts — which is where the contested row above comes from. It has never been the in-run judge, so it has never gated, critiqued or driven the loop.
  • OpenNobody has opened the page in a browser from a session that could report back. The script parses and every field is produced — that is not the same as it looking right.

When something is wrong

# what a service thinks it is: public?, limits, telemetry, peers
curl -s $URL/api/health | python3 -m json.tool

# each agent reports its own brain, model, search config, telemetry
TOK=$(gcloud auth print-identity-token)
curl -s -H "Authorization: Bearer $TOK" https://research-gcp-wgcq55zbfq-uc.a.run.app/health

# the last run's calls, with provider request ids
curl -s $URL/api/timeline

Failure kinds are load-bearing. provider means the remote answered and declined; protocol means the reply never arrived. Filing the first as the second turns "Bedrock refused the topic" into "AgentCore broke A2A". The request_id in the timeline is the provider's own — paste it into CloudWatch or Cloud Logging. It is the only column here that someone outside the process can check.

Traps already paid for

  • Cost a dayA control that cannot run is not a control that passed. Two separate causes produced six clean-looking denials while nothing was tested.
  • Corrupts a runNever edit a script while verify is running. Bash reads a script incrementally.
  • SilentThe controls job runs built_image() — the image from the last deploy. A code change is not in it until you redeploy.
  • Silentgcloud run jobs execute --wait prints nothing on stdout. Use --async if you need the execution name.
  • Lost a dayWork that is deployed but not committed does not exist.
  • Rots quietlyAn open-items list decays as fast as the work closes it, and nothing fails when it does. Four items on this page's repo twin stayed "open" for four days after they were finished, contradicting the same file's status section.
